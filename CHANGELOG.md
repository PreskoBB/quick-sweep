# Changelog

## 1.0.5

- **The GPU card works on AMD and Intel graphics, not only NVIDIA** (GitHub issue #2: a Radeon RX 580 showed "-- °C", "No NVIDIA GPU found" and an empty VRAM bar). The GPU is now read through a chain of sources and merged field by field: (a) NVIDIA through NVML, exactly as before; (b) LibreHardwareMonitor, the library that already reads the CPU, for AMD Radeon, Intel Arc and anything else it lists: core (else hot spot) temperature, load, VRAM used and total, fan and power. It reads AMD's display library in user mode, so it needs neither administrator rights nor the PawnIO driver; (c) Windows' own GPU performance counters, the figures Task Manager shows, for any GPU on any driver: usage (the busiest 3D or compute engine of that adapter, the processes added up per engine) and dedicated VRAM in use, with no admin. The adapter name and dedicated memory size come from DXGI (the registry when DXGI fails). A source that reports exactly 0 for usage or VRAM while the counters show real activity is not believed.
- **Which GPU is shown.** The discrete GPU first (integrated graphics only when nothing else is installed), and among several the one with the most dedicated memory. Software adapters ("Microsoft Basic Render Driver") never count. The card title is the real product name ("Radeon RX 580", "RTX 3060", "UHD Graphics 630").
- **No sensor is not an error.** A GPU whose driver exposes no temperature shows "--" and a small "no sensor" hint (the tooltip says why) instead of an error; load, VRAM and fan still show. Every "No NVIDIA GPU found" is gone; "No GPU found" appears only when Windows lists no usable adapter. The tray icon keeps "--" for the GPU row and puts the GPU load in its tooltip. The "GPU is running hot" alert only exists for a GPU with a temperature.
- **Game Mode and the after-game summary use the same readings**, so the GPU-load check works on AMD and Intel (including through the counters). A session with no GPU temperature says so ("no temperature sensor on this GPU", "GPU peak load 91%") instead of showing 0 °C. Sessions saved by earlier versions load unchanged.
- **Settings > status** lists the GPU, which source gave the temperature, usage and memory, and the state of every source. The log gets the same lines when the choice changes.
- New switch `QuickSweep.exe --gpu-probe=<file>`: asks every GPU source on its own (adapters, NVML, every sensor LibreHardwareMonitor lists, the raw counters, what Quick Sweep would show) and writes the result to a text file. For a PC whose GPU shows "no sensor" or odd numbers; run it from a normal prompt, it changes nothing. `--shots --demo --demo-gpu=amd` renders the flyout with an AMD card that has no temperature sensor.

## 1.0.4

- **Network charts can be read.** Move the pointer over either chart: the sample nearest to it gets a vertical marker line and a highlighted point, and a small readout shows the time (`HH:mm:ss`, local) and the latency in ms, or "lost" for a dropped packet. The readout stays inside the chart and does not flicker (it only redraws when the nearest sample changes); while you are reading a point the chart holds still instead of scrolling, and catches up when the pointer leaves.
- **Replies above the chart's 500 ms ceiling are no longer anonymous.** The chart still draws them at the top edge, but now as a red up-arrow labelled with the real value, and the readout shows the true latency, so a 2,000 ms spike no longer looks like a 510 ms one.
- **Peak and current value above each chart**, for example `now 18 ms · peak 412 ms at 21:14 · avg 17 ms · loss 2.1% (4 lost) · 3 spikes`. Loss only appears when packets were lost.
- **After-game summary:** a game with a ping spike or lost packets gets one extra line on the Sessions page: the worst ping (value, time, router or internet) and the number of lost packets. Quiet sessions show nothing. Sessions saved by 1.0.3 have no time for their worst ping and no packet count; the time is left out and the count is estimated from the saved loss percentage.
- The ping history already stamped every reading with its time; it now keeps about 5 hours (was 2.5), still a fixed-size buffer, so a long game's worst ping is not lost from the summary.
- Screenshots: `--shots --demo` renders the Network page with a hover readout on each chart (no real pointer needed).

## 1.0.3

- **The alert banner in the flyout was blank.** The "1 issue" badge and the yellow banner appeared, but no text was drawn: the alert's title and message were public fields, and a WPF binding only reads properties. They are properties now, every alert type (heat, full C:, kernel memory, leaks, drives) shows its title and a short message, a red banner marks a serious one, and clicking a banner opens the page that explains it (Drive health for a drive alert, Memory, Disk cleaner, Sessions). Tests read the real XAML and fail if a banner binding does not point at a property.
- **Drive health is calmer about damage that is not growing.** A reallocated-sector count that is the same as in the remembered baseline is now a warning ("has old damage: 296 reallocated sectors, unchanged since 11 Oct. Keep a backup of anything important on it"), no longer "failing". A count that grows, or any pending or uncorrectable sector, is critical ("is getting worse" / "is failing"). A drive seen for the first time with reallocated sectors is a warning until a second reading shows whether it grows. Warnings show in the flyout banner and on the Drive health page but never send a notification; a warning that becomes critical notifies once.
- **Cable (CRC) errors are judged as a cable problem.** More than 100 interface (UDMA CRC) errors is a warning ("cable problem: reseat or replace the SATA cable"), and critical only while the count keeps rising since the baseline. The baseline now stores the CRC count; a baseline file from 1.0.2 has none, so the first check after the update starts remembering it instead of calling a high count "rising". A counter that goes down lowers the baseline, so a later rise is still noticed.
- **The kernel-memory alert no longer fires on a big pool alone.** It needs a large pool (6 GB by default, or a fast climb from 3 GB) **and** memory under pressure: available RAM under 2 GB, or committed memory above 90 % of the limit. Once on, the limits loosen slightly so it does not flap. All three limits are in Settings under Alert limits.
- New demo switches for screenshots: `--demo-problem` and `--demo-problem=worse` (with `--shots --demo`) show a drive with old damage and a cable problem, or a drive whose damage is growing.

## 1.0.2

- **Installer permission check fixed.** The check that the folder Quick Sweep is installed into is administrators-only skipped every permission entry that is only inherited by files and folders created later. Now any inheritable entry that gives a non-administrator the right to write, delete or change permissions makes the folder untrusted (only the CREATOR OWNER and CREATOR GROUP placeholders are excused, and only when inherit-only). Generic write and all-access rights count too.
- **The installer writes a complete security descriptor instead of editing permissions.** Editing with `icacls /grant:r` only replaces the accounts it names and leaves every other explicit entry in place; on the hosted runner that left an explicit FullControl entry for the account that runs the installer, which a normal program of that account can use to rewrite the folder, so the folder was (rightly) judged untrusted and an installer test failed. Now the owner is Administrators and the permission list is replaced as a whole by a protected list holding exactly SYSTEM (full control), Administrators (full control) and Users (read and execute), written to the install folder before anything is copied in and to every copied file and folder afterwards, one item at a time. Each item is read back and the installer stops if it differs. A new state folder is created with that protected list as part of its creation, so there is no moment in which it inherits ProgramData's permissions.
- **An existing data folder is checked before it is touched.** Any user can create `C:\ProgramData\QuickSweep` before the installer runs. The installer used to re-own and reset what it found there and only then check it, which turned planted content into "trusted" content. Now the existing folder is judged first (owner, permissions, no junction or symbolic link anywhere inside, every item administrators-only); if anything fails, the whole folder is renamed aside (never re-owned, reset or deleted) and a new one is created. Only files the installer itself creates or copies get their permissions set. The same full check now applies to an old data folder before settings are copied from it.
- **No link is followed as an administrator.** The recursive `icacls ... /T` calls, which follow junctions and symbolic links, are gone: trees are walked in PowerShell without following links, a link anywhere stops the step before anything is changed, and removing a tree (installer and uninstaller) deletes a link as a link and never enters it. The uninstaller deletes the data folder only if it passes the checks above; otherwise it leaves it, and the per-user folder, in place and says so, because deleting by path as an administrator inside a folder a normal program can write to can be raced with a link. The one `icacls` call left is a fallback for setting a single item's owner.
- **A new data folder is created in one atomic step.** It is created with `CreateDirectoryW` together with its protected permissions (no moment in which it inherits ProgramData's), and `ERROR_ALREADY_EXISTS` means somebody else got there first: that folder is not adopted or checked, it is renamed aside and a new one is created. The call is made from a small in-memory type, not through `Add-Type`, which would compile into the user's temp folder.
- **The installer and uninstaller load their PowerShell modules by full path** from the Windows PowerShell system folder, and run themselves again in Windows PowerShell 5.1 when they are started from PowerShell 7. A PowerShell 7 window used to hand its own module path to the 5.1 process, which then could not load `Microsoft.PowerShell.Security`. This is also what broke two of the installer-script tests on the 1.0.1 workflow run.
- The app's own check of its data folder now also recognises inherited entries stored with generic rights.
- Added a canary test that the standard-user CI job really runs without administrator rights, and tests for the cases above (inherited entries, a PowerShell-7-style module path, the permission check of a whole tree). The administrator-only permission test prints the checks' reasons and the owner and SDDL of everything it looked at when it fails, so a CI failure explains itself.

## 1.0.1 (tagged, never released: its workflow run failed; everything in it is in 1.0.2)

- **The installer and uninstaller no longer trust environment variables.** Locations come from Windows' known folders, `PATH` and `PSModulePath` are reset to the system folders, winget is only run from its own package folder, the install folder must be administrators-only before anything is copied, and the logon task is read back after registration to check that it points at the program below the real `Program Files`. The batch file starts PowerShell from the system folder by absolute path.
- **Protected folders.** `?` now stands for one character. A relative path, a bare folder name, a network path, a `..` or an unknown `%variable%` is ignored and flagged inline in Settings (a line that is valid but matches no folder right now gets a note).
- **Personal folders** (Documents, Desktop, Pictures, Videos, Music, Downloads, OneDrive) are looked up through the known-folder API for the interactive user, so a folder moved to another drive is protected where it really is.
- **CI.** Read-only workflow token; a separate release job that only uploads; a best-effort job that runs the tests marked "non-admin" as a freshly created standard user.
